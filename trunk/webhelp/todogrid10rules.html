Overview

The configuration allows you to adapt the examination of the files very individually to the respective situation (examination of C files is currently not available). Detailed information about the way of scanning and parsing your source files is explained in this page.

 

What is a ToDo?

In the context of "ToDo Grid" a ToDo is any individual text within the source code that complies with the following rules. To separate this text from the code to be compiled, the text is marked as a comment. You can use // for single line ToDo and (* *) or { } for multi line ToDo.

After the start of the comment section, an inserted keyword (token) identifies and specifies the following text. The definition of the token is essentially free; however, if you're working within a group of programmers, there will be rules that must be observed. Thanks to the ability to individually activate / deactivate the tokens to be considered for scanning, adaptation to the specific work situation is very easy.

 

How to insert (and remove) ToDo

Of course, the entries can be entered manually, but it is faster if you use pre-made templates. To insert pre-made entries, you can use the "source code templates" available in the IDE, which can be accessed via Ctrl+J. Alternatively, you can also use the "Code Librarian" expert. In both cases, regular ToDo texts must be created first, which can then be quickly inserted later.

In a multi line ToDo, the token should be placed on the line where the comment begins. The number of lines read and evaluated in a multi line ToDo is limited; no more than 5 lines should be used.

In order to keep the time required for scanning the files as short as possible, ToDo that are no longer needed should also be removed from the source - a perhaps unspectacular task, but one that should nevertheless be carried out regularly (even within a working group)!

 

Rules of syntax analysis

The following rules are intended as a general background, which can be consulted if the scan results do not meet your expectations. With individual use, a personal approach will quickly develop, so that these comprehensive rules will be followed almost automatically. However, it's definitely worth reading through ...

 

Structure of ToDo

The scan function of "ToDo Grid" allows a large number of structural variations of the ToDo entries. This is particularly important when editing external source code whose formatting cannot be sufficiently influenced.

In general, ToDo entries should be as short and clear as possible. No long texts should be stored here, it is recommended to use single-line ToDo entries.

▪The simplest ToDo entry consists of a token and a description text, for example:

//TODO : This is to be done

 

▪Spaces may be inserted between the comment introduction and the token, but it is recommended not to do so.

 

▪The token is not recognized case-sensitive. As already mentioned, the definition of tokens is essentially free (this is done in the configuration). However, if you're working within a group of programmers, there will be rules that must be observed.

 

▪The separation between token and text can be done by spaces or a colon. Multiple spaces are allowed, but for space reasons, this should not be overdone. If a number is at the beginning of the description text, it must be separated by a colon (otherwise the number will be considered as priority).

 

▪The description should be as short and concise as possible. If the scan does not find a description in an otherwise valid ToDo entry, the message "No description found" is displayed in the string grid.

▪More complex ToDo can optionally contain additional categories and owners, for example:

//TODO -cCategory -oOwner : This is to be done

 

▪Of course, each parameter can be specified alone. The category is introduced by the -c parameter, the owner is introduced by the -o parameter. Any number of (or no) spaces can be inserted before, between, and after the parameters. To ensure good readability, it is recommended to insert a space before, between and after the parameters.

 

▪The terms are generally freely definable, but may not contain any spaces or hyphens and must be placed immediately after the parameter. For ease of analysis, the definition set of categories and owners should be as small as possible.

 

▪The application optionally provides the ability to assign category and owner to a token (see configuration). In case of a conflict between the term used in the source and the token assignment, the term used in the source is displayed in the string grid.

 

▪If the parameters -c and -o are specified multiple times, only the first occurrence is evaluated; the order of the two parameters is not relevant.

▪Last but not least, each ToDo entry can be given a priority.

//TODO N -cCategory -oOwner : This is to be done (with N=1..5)

 

▪The priority can be specified by a single-digit number after the token. There must be one or more spaces between the token and the number. If there is no space between the token and the number, the number is considered part of the token. It is recommended to add a space before and after the number.

 

▪The digits 1..5 are considered the 5 priority levels declared by the application. The digits 0 and 6..9 are mapped to 5, which means "Lowest" priority.

 

▪The application optionally provides the ability to assign a priority to a token (see configuration). In case of a conflict between the value used in the source and the token assignment, the value used in the source is displayed in the string grid.

 

Datascan

▪The directories to be included in the scan are defined in the configuration. It's particularly noteworthy that a large number of directories can be defined there, but the currently relevant set can be selected by simply marking the appropriate items.

Of the lists imported from the IDE, files with the extensions  dpr ,  pas ,  inc  and  todo  are checked for the presence of tokens. This setting cannot be changed and corresponds to the "ToDo List" expert.

▪In addition to the file lists imported from the IDE, any additional directories can be stored in the configuration. For each entry you can specify whether sub directories should also be read. Here, too, the currently relevant set can be selected by simply marking the appropriate items.

For the additional directories any extensions to be considered can be defined. And here, too, the currently relevant set can be selected by simply marking the appropriate items.

▪The tokens used to check the files are also defined in the configuration. And of course, you can select the currently relevant set by simply marking the corresponding elements.

▪Since the speed of the syntax analysis is largely determined by the number of comparisons, only the actually relevant set of directories, file extensions and tokens should be activated for the scan.

▪After each scan, the status bar displays the number of files examined, their line count, and the total duration of the scan.

 

Suggestions for efficient use

If your personal work situation does not impose any mandatory rules or at least allows temporary arrangements, you should use the extended features of "ToDo Grid" as creatively as possible. The "control center" for this is the configuration window; detailed information can be found under Configuration, Tokens to scan.

▪As already stated above, ToDo entries and especially the description text should be as short and clear as possible - long texts are inappropriate! It is recommended to use single-line ToDo entries.

▪Not all possible variations of tokens and additional information may be the right solution for your individual case - check what your needs really are.

▪The application allows the definition of a large number of tokens, but this should not tempt you to create an unnecessary number of tokens - "brevity is the soul of wit". The ability to create a large number of tokens is primarily intended to cover different work areas and to only activate the relevant amount at any given time.

▪Critically evaluate whether specifying a category / owner makes sense. Only a limited amount can be filtered properly in the string grid.

•The selection of categories to use must, of course, meet individual requirements, but here, too, the rule is to use as few categories as possible.

•Initials should be used to indicate the owners if possible.

▪You should examine even more critically whether setting priorities makes sense. If there are entries years old with the "Critical" rating, the use of priorities may seem questionable. In any case, you should think about which differentiation of priorities makes sense in light of your processing options.

▪The application offers significantly expanded possibilities to assign additional attributes to a token. Optionally, priority, category, and owner can be encoded directly into the token. This generally creates a particularly space-saving ToDo entry and allows a very fast insertion into the source. However, it should be noted that the entry in the source is no longer readable as usual and all participants must have the "ToDo Grid" expert available in order to receive the necessary decoding in the display.

▪In older Delphi versions, bookmarks are not saved by the IDE and the "Editor Bookmarks" expert doesn't do this either - that can be quite annoying! The "ToDo Grid" expert can help here by using the ToDo entry as a jump target. But please don't forget to remove these targets when they are no longer needed!

▪It is recommending to standardizing the insertion and structure of ToDo entries. For this purpose, you can use the source code templates in the IDE (accessible via Ctrl+J) or the "Code Librarian Expert" from GExperts.
